# Защита учётных записей

## Первый администратор во всех вариантах установки

Backend поддерживает `BOOTSTRAP_ADMIN_USERNAME` (по умолчанию `admin`) и
`BOOTSTRAP_ADMIN_PASSWORD`. Непустой пароль включает создание отсутствующего
логина с ролью администратора при запуске приложения. Правила: логин 3–64
символа в формате обычного сотрудника, пароль 12–256 символов.

`scripts/setup_env.py` генерирует уникальный пароль при создании новой `.env`,
не выводит его в терминал и не перезаписывает существующую `.env`. Для Linux
новый файл создаётся с режимом 0600; в Windows доступ определяется ACL папки.
Пароль прочитайте локально из `.env`, войдите в режиме «Сотрудник», смените его
и очистите bootstrap-пароль в конфигурации. Пароль аккаунта хранится как
scrypt-хеш; bootstrap-секрет до очистки остаётся открытым в конфигурации.

Windows, Linux и systemd используют один startup-механизм; Docker Compose
передаёт параметры из `.env` через `env_file`. На существующих установках
параметры добавляются вручную, затем backend перезапускается (для Compose —
с пересозданием контейнера). Пустой пароль сохраняет прежний вход по API-key.

Существующий логин **не изменяется**, включая пароль, роль, активность и 2FA.
Изменение bootstrap-секрета не сбрасывает пароль. Если пользователь уже есть,
смените пароль штатным API/UI. Если логина ещё нет и конфигурация некорректна,
приложение не запускается; значение пароля не включается в сообщение ошибки.

Это автоматическое создание, а не перенос БД: настройки и 2FA другого сервера
не копируются. Секреты передаются защищённо вне Git; одинаковый пароль на всех
публичных установках не предоставляется.

## Пароль и сессии

Каждый сотрудник может изменить собственный пароль и завершить собственные сессии независимо от роли. Изменение пароля требует текущий пароль и завершает все сессии. Эти операции сохраняют проверку CSRF и не дают права менять чужие аккаунты.

## Двухфакторная аутентификация

Подключение требует текущий пароль. QR-код создаётся локально в интерфейсе; секрет не передаётся внешним сервисам. Незавершённая настройка действует 10 минут и не изменяет уже включённую защиту. Повторный вызов подключения для защищённого аккаунта отклоняется.

Для отключения нужны текущий пароль и новый шестизначный код из приложения. Один временной шаг можно использовать только один раз, включая код подтверждения подключения. Если код уже использован при входе, дождитесь следующего. При включении и отключении 2FA сохраняется текущая сессия, остальные отзываются.

Проверка использует TOTP SHA-1 с периодом 30 секунд и допуском одного шага. Защита от повторного использования хранится в БД и обновляется условным атомарным запросом. Подбор кодов и подтверждений пароля ограничен; лимит попыток хранится в памяти процесса. Для эксплуатации с несколькими API workers нужен общий rate limiter.

## Обновление существующей установки

Перезапуск backend добавляет совместимые колонки pending-настройки, её срока действия и использованного шага. Уже активные TOTP-секреты и пароли не заменяются. Незавершённое подключение старой версии следует начать заново. Перед обновлением рабочей установки необходима резервная копия БД.

## Известные ограничения

- Секреты TOTP пока не зашифрованы в БД: ограничьте доступ к БД и резервным копиям. Шифрование требует отдельно управляемого ключа и процедуры его восстановления; API_KEY не следует использовать для этого автоматически.
- Коды восстановления и пользовательское восстановление при потере приложения ещё не реализованы. Сохраните доступ к приложению-аутентификатору; не считайте административный API-ключ защищённым этим пользовательским TOTP.
- Административный API-ключ остаётся отдельным доверенным способом входа. Храните его только у администратора; в production используйте HTTPS и secure cookies.
- Долговременная доставка уведомлений, много-процессные ограничения попыток и конкурентное изменение аккаунта во время выдачи сессии требуют отдельной эксплуатационной проверки.
