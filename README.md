## О проекте

**School Security Analytics System** — веб-приложение для видеомониторинга, анализа изображений и проверки событий оператором. Оно объединяет RTSP-камеры, нейросетевые детекторы и архив в одном рабочем пространстве.

Система помогает заметить объекты и ситуации, требующие внимания: обнаруженную собаку, объект, распознанный специализированной моделью как оружие, или длительно неподвижную сумку без человека рядом. Решение о характере события принимает сотрудник, а не нейросеть.

```text
RTSP-камеры → Захват кадров → Детекторы YOLO → Проверка события во времени
                                                        ↓
Веб-интерфейс ← Камеры, статистика, архив ← Фото и видеоклип
                      ↓
             Проверка сотрудником
```

> [!IMPORTANT]
> Проект — **прототип для контролируемых испытаний**, а не сертифицированная система охраны. Он не заменяет охрану и другие меры безопасности. Качество на реальных школьных камерах пока не подтверждено независимыми испытаниями.

### Технологии

- **Backend:** Python, FastAPI, SQLAlchemy, OpenCV, Ultralytics / PyTorch.
- **Frontend:** React, TypeScript, Vite, Tailwind CSS.
- **Локальный запуск:** SQLite, обучение в отдельном локальном процессе.
- **Docker Compose:** Nginx, API, PostgreSQL, Redis и Celery worker.
- **Авторизация:** scrypt-хеши паролей, серверные сессии, HttpOnly/SameSite-cookie и CSRF-проверка изменений.

### Требования

- **Python 3.13** — версия, на которой проверены зависимости проекта.
- **Node.js 22.12+ из ветки 22 LTS** и npm — для запуска интерфейса без Docker.
- **Git** — для скачивания и обновления исходников.
- **FFmpeg** — рекомендуется установить системно; при его отсутствии предусмотрен fallback через `imageio-ffmpeg`.
- Доступ в интернет для установки зависимостей и загрузки отсутствующих весов.

NVIDIA GPU не обязательна для знакомства с системой. Производительность зависит от модели, разрешения и числа камер. Начинайте с **YOLO N и одной камеры**; единого обещанного FPS или универсальных требований к памяти нет. GPU-окружение PyTorch/CUDA настраивается отдельно; Compose не включает GPU-проброс.

## Установка на Windows

Команды ниже выполняются в **PowerShell**. Проверенный вариант — Python 3.13 и Node.js 22 LTS.

### 1. Установите инструменты

Если используется Windows Package Manager:

```powershell
winget install --id Git.Git -e
winget install --id Python.Python.3.13 -e
winget install --id OpenJS.NodeJS.22 -e
winget install --id Gyan.FFmpeg -e
```

Либо установите их с официальных сайтов: [Git](https://git-scm.com/downloads), [Python](https://www.python.org/downloads/), [Node.js](https://nodejs.org/), [FFmpeg](https://ffmpeg.org/download.html). При установке Python включите добавление в PATH, если планируете использовать команду `python`.

**После установки откройте новое окно PowerShell** и проверьте:

```powershell
git --version
py -3.13 --version
node --version
npm.cmd --version
```

### 2. Скачайте проект и установите backend

```powershell
git clone https://github.com/maisaak/School-Security-Analytics-System.git
cd School-Security-Analytics-System

py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
.\.venv\Scripts\python.exe scripts/setup_env.py
```

Скрипт создаст `.env` со случайными секретами, включая уникальный пароль первого администратора. Существующий `.env` он **не перезаписывает**. Учётная запись создаётся при первом запуске backend.

### 3. Запустите backend

Из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

Оставьте терминал открытым. Здесь не требуется активация виртуального окружения, поэтому менять ExecutionPolicy PowerShell не нужно.

### 4. Запустите интерфейс

Откройте **второй терминал** в папке проекта:

```powershell
cd frontend
npm.cmd ci
npm.cmd run dev
```

Откройте **http://localhost:3000** и перейдите к [первому входу](#первый-вход).

sudo apt install -y python3.13 python3.13-venv

Если установлен nvm, выберите Node.js 22:

```bash

```

Если `apt` не находит Python 3.13, не подменяйте его произвольной старой версией: используйте подходящий вашей ОС способ установки Python или [Docker](#запуск-через-docker).

## Сервер Ubuntu/Debian

Серверная схема **без Docker**: Nginx отдаёт production-сборку React и проксирует запросы к API на `127.0.0.1:8000`. Один backend-процесс управляется systemd: запускается после перезагрузки и перезапускается при аварии. Node.js нужен только для сборки — Vite на сервере не запускается. База по умолчанию — SQLite; обучение выполняется локально. Для PostgreSQL и отдельного Celery worker используйте [Docker Compose](#запуск-через-docker).

Инструкция рассчитана на **Ubuntu 24.04 LTS / Debian 13** с systemd, доступом `sudo` и доменом. Для других версий Debian/Ubuntu сначала проверьте доступность Python 3.13. Рекомендуемый начальный ресурс: 4 CPU, 8 ГБ RAM, SSD от 40 ГБ; это ориентир, а не гарантия производительности — число потоков и обучение требуют нагрузочных испытаний. Для реальных камер предпочтительна закрытая сеть/VPN.

> Linux/systemd/Nginx в текущем Windows-окружении не проверялись на живом сервере. Перед эксплуатацией проведите пробное развёртывание. Скрипт не настраивает GPU/CUDA, DNS и TLS автоматически и не заменяет резервное копирование.

### 1. Подготовьте ОС

```bash
sudo apt update
sudo apt install -y git curl ca-certificates build-essential nginx ffmpeg libgl1 libglib2.0-0 libgomp1
```

Нужны **Python 3.13** с `venv` и **Node.js 22 LTS** с npm. Debian 13:

```bash
sudo apt install -y python3.13 python3.13-venv
```

На Ubuntu 24.04 штатный Python другой версии. Не меняйте `/usr/bin/python3`! Можно отдельно собрать Python из официального исходного архива:

```bash
sudo apt install -y libssl-dev zlib1g-dev libbz2-dev libreadline-dev libsqlite3-dev libffi-dev liblzma-dev uuid-dev pkg-config
# Пример версии. Перед установкой выберите актуальное исправление ветки 3.13
# на https://www.python.org/downloads/ и проверьте подлинность архива.
curl -fLO https://www.python.org/ftp/python/3.13.9/Python-3.13.9.tgz
tar -xzf Python-3.13.9.tgz
cd Python-3.13.9
./configure --with-ensurepip=install
make -j2
sudo make altinstall
cd ..
```

Установите Node.js 22 через официальный пакетный репозиторий/бинарный дистрибутив, следуя [инструкции Node.js](https://nodejs.org/en/download). Важно: `node` и `npm` должны быть доступны системно, а не только в интерактивном `nvm`-окружении пользователя.

```bash
python3.13 --version
node --version
npm --version
```

### 2. Создайте пользователя и скачайте проект

Пути и пользователь ниже совпадают с готовыми файлами в `deploy/`. Не запускайте приложение от root.

```bash
sudo useradd --system --user-group --home-dir /opt/school-security --shell /usr/sbin/nologin school-security
sudo install -d -o school-security -g school-security -m 750 /opt/school-security
sudo -u school-security git clone https://github.com/maisaak/School-Security-Analytics-System.git /opt/school-security
cd /opt/school-security
sudo -u school-security python3.13 scripts/setup_env.py
sudo chmod 600 .env
sudoedit .env
```

Сохраните сгенерированный `API_KEY` отдельно. Проверьте `.env` (замените домен своим):

```dotenv
DEV_MODE=false
SEED_DEMO_CAMERAS=false
COOKIE_SECURE=false
CORS_ORIGINS=["https://school.example.org"]
ALLOW_LOCAL_WEBCAM=false
ALLOW_HTTP_CAMERAS=false
CAMERA_ALLOWED_HOSTS=["192.168.10.21","192.168.10.22"]
ENABLE_LOCAL_TRAINING=true
```

`COOKIE_SECURE=false` используется **только для первичной проверки HTTP**; после TLS обязательно включите `true`. Не выставляйте `DEV_MODE=true`, wildcard CORS или пустой API-ключ. Не переносите Windows `.venv` на сервер. Веса моделей можно перенести отдельно в `ml/models/`; не активируйте непроверенные модели. PostgreSQL требует собственной схемы бэкапов: локальный `backup_data.py` сохраняет только стандартный файл SQLite.

### 3. Установите сервис и Nginx

```bash
cd /opt/school-security
sudo bash scripts/deploy_server.sh school.example.org
sudo systemctl status school-security --no-pager
curl -f http://127.0.0.1:8000/api/system/status
curl -f -H 'Host: school.example.org' http://127.0.0.1/api/system/status
```

Скрипт устанавливает Python-зависимости, собирает интерфейс, публикует его в `/var/www/school-security`, устанавливает `deploy/school-security.service` и Nginx-конфигурацию. `.env`, база, медиа и модели не перезаписываются. Скрипт проверяет готовность API перед перезагрузкой Nginx. После нескольких сбоев подряд systemd останавливает повторные запуски: устраните причину и выполните `sudo systemctl reset-failed school-security`, затем `sudo systemctl restart school-security`.

Убедитесь, что DNS домена указывает на сервер. Скрипт не удаляет другие сайты Nginx. Если обращаетесь по IP, можно увидеть стандартный сайт — используйте домен или корректный заголовок Host. Медиа остаются защищены авторизацией backend; не публикуйте `media/`, `.env` или каталог проекта напрямую через Nginx.

### 4. Включите HTTPS и ограничьте доступ

Для публичного домена с корректным DNS и доступными 80/443:

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d school.example.org --redirect
sudo certbot renew --dry-run
sudoedit /opt/school-security/.env
# Установите COOKIE_SECURE=true, затем:
sudo systemctl restart school-security
```

Если используется UFW, сначала сохраните SSH-доступ (для нестандартного SSH-порта откройте именно его). Не включайте firewall вслепую на удалённом сервере:

```bash
sudo apt install -y ufw
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'
sudo ufw enable
sudo ufw status
```

Порты 8000, 3000, БД и Redis наружу **не открывайте**. Для закрытой школьной сети используйте VPN и внутренний доверенный сертификат вместо публичного Certbot. Сертификат без доверия на клиентских устройствах не обеспечивает нормальную эксплуатацию. После HTTPS войдите через вкладку **API-ключ** с ключом из серверного `.env`, создайте сотрудников и проверяйте их права; стандартная учётная запись `admin` автоматически не создаётся.

### 5. Резервное копирование

```bash
sudo -u school-security /opt/school-security/.venv/bin/python /opt/school-security/scripts/backup_data.py
sudo install -m 644 deploy/school-security-backup.service deploy/school-security-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now school-security-backup.timer
sudo systemctl list-timers school-security-backup.timer
```

Копии сохраняются в `/opt/school-security/backups/` ежедневно около 03:30; пропущенное задание выполняется после включения сервера. Успешная копия содержит `BACKUP_COMPLETE.txt`, неуспешная — `BACKUP_FAILED.txt`. SQLite копируется через Backup API, включая подтверждённые WAL-транзакции; целостность базы проверяется. Файлы медиа копируются последовательно: для полностью согласованного снимка остановите запись/обучение. `.env` не включён: храните его отдельно защищённо. Копии содержат персональные данные — ограничьте доступ, шифруйте перенос на другой носитель. Автоматического удаления старых копий нет: контролируйте свободное место и периодически проверяйте восстановление на отдельном стенде.

### 6. Обновление и диагностика

Перед обновлением сделайте копию и запишите текущий коммит (`git rev-parse HEAD`). Для согласованной копии остановите backend:

```bash
cd /opt/school-security
sudo systemctl stop school-security
sudo -u school-security .venv/bin/python scripts/backup_data.py
sudo -u school-security git pull --ff-only
sudo bash scripts/deploy_server.sh school.example.org
```

**Важно:** повторный запуск скрипта заново записывает HTTP-конфигурацию сайта Nginx. После него повторно выполните `sudo certbot --nginx -d school.example.org --redirect`, чтобы восстановить TLS, и проверьте HTTPS. Для площадок с собственными настройками Nginx обновляйте конфигурацию вручную, не перезаписывая её скриптом. При ошибке обновления не восстанавливайте старую БД поверх новой без проверки совместимости; сначала испытайте откат на копии.

```bash
sudo journalctl -u school-security -n 100 --no-pager
sudo journalctl -u school-security -f
sudo journalctl -u school-security-backup.service -n 50 --no-pager
sudo nginx -t
sudo tail -n 100 /var/log/nginx/error.log
sudo ss -ltnp
```

`502` от Nginx обычно означает, что API не запущен; `503` у `/api/system/status` — ошибка БД. Сначала изучите `journalctl`, а не переустанавливайте проект и не удаляйте базу. В сервисе оставлен **один worker**: несколько API-процессов дублируют управление камерами. GPU-драйверы/CUDA и ресурсы обучения настраиваются отдельно.

## Первый вход

1. Запустите backend и откройте **http://localhost:3000** (или `http://127.0.0.1:3000/`).
2. Если `.env` создан актуальным `scripts/setup_env.py`, первый запуск автоматически создаст администратора. На форме входа выберите **«Сотрудник»**.
3. Логин возьмите из `BOOTSTRAP_ADMIN_USERNAME` (по умолчанию `admin`), пароль — из `BOOTSTRAP_ADMIN_PASSWORD` в локальном `.env`. Пароль уникален для установки и не выводится в логи.
4. После входа измените первоначальный пароль в **«Настройки» → «Безопасность»**, затем создайте сотрудников в **«Настройки» → «Сотрудники»**.
5. Удалите первоначальный пароль из `.env` (оставьте `BOOTSTRAP_ADMIN_PASSWORD=`) после успешного создания и смены пароля. Сохраните действующие данные входа в защищённом хранилище.

**Общего пароля по умолчанию нет.** Если bootstrap выключен или используется старый `.env`, выберите **«API-ключ»**, войдите со значением `API_KEY` и создайте администратора через раздел сотрудников. Не передавайте сотрудникам `API_KEY` и не публикуйте `.env`, скриншоты ключа или ссылки с секретами.

### Автоматическое создание администратора: Windows, Linux, systemd и Docker

Механизм общий для всех вариантов: он выполняется при запуске FastAPI после создания/обновления схемы БД и до запуска камер. Установщики Windows/Linux и ручные инструкции вызывают `scripts/setup_env.py`, который генерирует пароль для новой `.env`. В systemd backend читает `.env` из корня проекта; в Docker Compose файл передаётся через `env_file`.

Для собственной конфигурации задайте **до первого запуска**:

```dotenv
BOOTSTRAP_ADMIN_USERNAME=admin
# Вставьте собственный уникальный пароль длиной 12–256 символов.
BOOTSTRAP_ADMIN_PASSWORD=
```

Пустой пароль отключает создание. Для логина действуют обычные правила: 3–64 символа, строчные латинские буквы, цифры, `_`, `.` и `-`. Пароль сохраняется в БД только как scrypt-хеш. Некорректная конфигурация новой учётной записи останавливает запуск с сообщением без значения пароля.

**Существующий логин никогда не перезаписывается:** пароль, роль, отключённое состояние и 2FA остаются прежними, даже если bootstrap-пароль в конфигурации изменился. Это не механизм сброса пароля. Перезапуски и обновления не возвращают старые данные входа.

Для уже существующей `.env` добавьте параметры вручную — генератор намеренно не дописывает секреты в существующую конфигурацию. После изменения перезапустите локальный backend или `school-security.service`; в Compose выполните `docker compose up -d --force-recreate backend`. Не передавайте пароль в командной строке и не выполняйте вывод полной конфигурации Compose в общедоступные логи.

### Учётные записи при переносе на другой сервер

`git clone` и `git pull` переносят **код, но не сотрудников и пароли**. Созданный на одном компьютере `admin` существует только в его базе. Для автоматического создания аналогичной учётной записи на чистом сервере задайте bootstrap-параметры выше через его защищённую конфигурацию. Универсальных данных входа в исходниках нет.

Bootstrap создаёт новую учётную запись, но не переносит её настройки, 2FA или историю. Чтобы сохранить существующие учётные записи целиком, нужен защищённый перенос базы в рамках резервного копирования и восстановления, а не публикация базы в GitHub:

- для SQLite следуйте [инструкции backup/restore](docs/BACKUP_RESTORE.md); восстановление выполняется в новую папку, без перезаписи рабочей установки;
- для PostgreSQL используйте `pg_dump`/`pg_restore` с проверкой совместимости схемы;
- `.env` храните и переносите отдельно защищённым способом. При смене `API_KEY` прежние сессии перестают действовать; пароли сотрудников хранятся в базе в виде scrypt-хешей;
- база содержит не только сотрудников, но и другие настройки и историю. Не переносите её поверх действующей установки без отдельного плана и резервной копии.

Не добавляйте реальные пароли в README, установщики, `.env.example` или коммиты.

| Адрес | Назначение |
|---|---|
| http://localhost:3000 | Веб-интерфейс |
| http://localhost:3000/display | Полноэкранный режим видеостены для поста наблюдения |
| http://localhost:8000/docs | Swagger / документация API |
| http://localhost:8000/health | Проверка процесса API, не состояния всех камер |

На чистой установке камеры не создаются автоматически, а архив пуст. Это нормальное состояние, не ошибка запуска.

## Подключение камер

### Настоящая RTSP-камера

1. Назначьте камере статический IP и убедитесь, что сервер видит её в сети.
2. Добавьте разрешённые IP в `.env`:

   ```dotenv
   CAMERA_ALLOWED_HOSTS=["192.168.1.20","192.168.1.21"]
   ```

3. Перезапустите локальный backend. Для Docker выполните:

   ```bash
   docker compose up -d --force-recreate backend celery_worker
   ```

4. В разделе мониторинга нажмите добавление камеры и укажите её настоящий RTSP-адрес, например:

   ```text
   rtsp://USER:PASSWORD@192.168.1.20:554/stream
   ```

Путь потока зависит от производителя. Проверить адрес можно заранее в VLC. В рабочем режиме разрешены явно указанные IP; loopback, link-local и служебные имена блокируются. HTTP-источники по умолчанию отключены. Проверка URL в приложении не заменяет исходящий firewall и изоляцию сети камер.

### Знакомство без оборудования

Добавьте одну из демонстрационных камер вручную:

```text
sim://entrance
sim://hallway
sim://courtyard
```

Это синтетические сцены для проверки интерфейса и интеграции, **не доказательство качества на реальном видео**. Старые демонстрационные веса `school_security_best.pt` не активны по умолчанию.

## Модели YOLO и настройки

### Выбор базовой модели

В разделе **«Настройки» → «Детекция»** администратор может выбрать:

| Семейство | Размеры | Назначение |
|---|---|---|
| YOLOv8 | N / S / M / L / X | Базовый COCO-детектор объектов |
| YOLO11 | N / S / M / L / X | Альтернативный базовый COCO-детектор |

**N** — наиболее лёгкий вариант семейства; более крупные модели требуют больше ресурсов. Выбор должен опираться на замеры FPS и качества на ваших сценах, а не только на размер модели.

Если весов нет, разрешите загрузку официальных файлов и нажмите **«Применить модель»**. Нужен доступ к GitHub. Перед переключением выполняются проверка и прогрев; при ошибке загрузки/проверки прежний детектор остаётся активным. Выбор общий для камер и сохраняется в БД.

> Стандартные COCO-веса YOLOv8/YOLO11 **не являются специализированным детектором оружия**. Оружейная модель и активные кастомные веса остаются отдельными. Новые задачи обучения используют выбранную базовую модель.

### Сотрудники и роли

| Роль | Права |
|---|---|
| Директор | Просмотр камер, архива, аналитики и своих настроек |
| Охрана | То же + анализ фото/видео и подтверждение инцидентов |
| Администратор | То же + управление камерами, удаление записей, модели, обучение и сотрудники |

Логин: 3–64 символа, строчные латинские буквы, цифры и допустимые разделители; пароль: от 12 символов. Таблица описывает системные роли. Для пользовательских ролей обнаружены пробелы серверного разграничения прав: отсутствие `view_monitoring` пока не запрещает чтение мониторинга и медиа, а `manage_cameras` разрешает часть операций, задуманных как admin-only. См. [аудит](docs/SECURITY_AUDIT.md).

Отключение, смена роли или пароля отзывает сессии сотрудника для новых запросов; выход отзывает текущую сессию. Уже открытый MJPEG-поток пока не перепроверяет доступ. Ротация `API_KEY` аннулирует сессии для последующих запросов. Настройка TOTP доступна в **«Настройки» → «Безопасность»**; секреты TOTP в текущей версии хранятся в БД без шифрования.

### Длительность записи нарушения

В **«Настройки» → «Детекция» → «Запись нарушения»** задаются секунды **до** и **после** срабатывания: целые числа от 0 до 30, по умолчанию **5/5**. Значения общие для всех камер, сохраняются в БД и применяются к новым срабатываниям без перезапуска. Начатый клип использует прежние значения; старый архив не изменяется.

Предыстория хранится в JPEG-буфере с лимитом памяти; после запуска, обрыва связи или достижения лимита доступная предыстория может быть короче. Клип формируется по временным меткам кадров. **Инцидент появляется в архиве и отправляется в уведомления только после post-roll и кодирования.** Одновременно сохраняется один клип на камеру; это ограничивает обработку новых срабатываний в этот период.

### Персональный интерфейс

Каждый сотрудник может сохранить 1–8 колонок видеостены, тему, акцентный цвет, Liquid Glass, прозрачность, скругления, показ блоков, компактный режим, анимации и стартовую вкладку. На узких экранах сетка адаптируется. Скрытие блока не меняет права доступа и не останавливает запись событий.

## Обучение на своих данных

Система обучает **кандидата**, а не автоматически заменяет рабочую модель.

1. Соберите реальные данные с разрешением на использование. Разделяйте train/val **по камерам или времени съёмки**, а не по соседним кадрам одного ролика. Для итоговой оценки оставьте независимый test-набор.
2. Разметьте **все** объекты целевых классов. Встроенный редактор рассчитан на один объект; для сложных сцен используйте внешнюю полную YOLO-разметку.
3. Загрузите данные через интерфейс или подготовьте структуру:

   ```text
   ml/datasets/custom/
   ├── images/
   │   ├── train/*.jpg
   │   └── val/*.jpg
   └── labels/
       ├── train/*.txt
       └── val/*.txt
   ```

4. Откройте **«Обучение»** и запустите задачу. Проверяются файлы, рамки, классы, точные дубликаты train/val и отсутствие синтетических `seed_*`. Минимум 6 train / 3 val — технический порог, **не достаточный объём для качества**.
5. Кандидат появится в `ml/models/candidates/job_ID.pt` со статусом `ready`. Камеры продолжают работать с прежней моделью. Каждый запуск — transfer learning от выбранной COCO-базы, не продолжение предыдущего обучения.
6. Проверьте кандидата отдельно на независимых данных. Только после этого нажмите **«Применить после проверки»**. Для возврата можно применить прежний кандидат, если его файл сохранён.

Формат строки разметки: `class_id center_x center_y width height`, координаты нормированы в 0–1. Классы: `0 dog`, `1 weapon`, `2 suspicious_bag`. Последний класс означает сумку-кандидат, а не её содержимое или намерения владельца.

Не используйте чужие непроверенные `.pt`: сериализованные модели требуют доверия к источнику. При аварийном завершении обучения статус может остаться `queued/running`; автоматическое восстановление таких задач пока не реализовано.

## Проверки для разработчиков

Из корня проекта, используя Python виртуального окружения:

```powershell
# Windows
.\.venv\Scripts\python.exe -m pytest -q
```

```bash
# Linux
.venv/bin/python -m pytest -q
```

Проверка frontend из папки `frontend` (`npm.cmd` вместо `npm` в PowerShell):

```bash
npm ci
npm test
npm run build
npm audit
```

Последняя проверка на Windows: **141 backend-тест прошёл, 1 пропущен**, включая 7 проверок автоматического создания администратора; **22 frontend-теста прошли**, TypeScript/Vite-сборка успешна. Пропущен symlink-тест из-за разрешений Windows; есть предупреждение об устаревшей связке Starlette TestClient/httpx. API-тесты используют временные БД/медиа; многие ответы детектора подменены для воспроизводимости. Это не benchmark точности моделей и не результат свежего CVE-аудита зависимостей.

Тесты `backend/tests/test_security_audit.py` включают **характеризационные доказательства уязвимостей**: их успешное выполнение не означает, что проблемы устранены. Подробности — в [отчёте безопасности](docs/SECURITY_AUDIT.md).

`scripts/smoke_live.py` — ручная проверка работающих API и интерфейса с временной sim-камерой. Скрипт создаёт и удаляет собственные тестовые данные; не запускайте его на загруженной боевой установке.

## Частые вопросы

<details>
<summary><strong>Интерфейс не подключается к серверу</strong></summary>

Проверьте http://localhost:8000/health и вывод backend. Для локального запуска нужны два работающих терминала. В Docker посмотрите `docker compose ps` и `docker compose logs backend`. Порты 3000 и 8000 должны быть свободны; открывайте именно адрес, указанный в инструкции.

Если во встроенном браузере зависает `localhost:3000`, попробуйте **http://127.0.0.1:3000/**. В локальной проверке этот адрес устранил зависание загрузки ролей и настроек записи; причина различия не установлена. Это другой origin: может потребоваться повторный вход, а browser-local настройки не обязаны переноситься.

</details>

<details>
<summary><strong>Камера отклонена или не показывает видео</strong></summary>

Проверьте IP в `CAMERA_ALLOWED_HOSTS`, перезапуск backend после изменения `.env`, логин/пароль и RTSP-путь. Проверьте поток в VLC с машины сервера. Для Docker дополнительно проверьте доступность камеры из контейнерной сети. Не отключайте сетевые ограничения ради обхода ошибки.

</details>

<details>
<summary><strong>YOLO11 не скачивается или работает медленно</strong></summary>

Для загрузки нужен доступ к GitHub и достаточно свободного места. Начните с YOLO11 N; крупные модели требуют больше ресурсов. При ошибке загрузки/проверки рабочий детектор не заменяется. Статус установленного файла сам по себе не подтверждает качество модели.

</details>

<details>
<summary><strong>PowerShell блокирует npm или активацию venv</strong></summary>

Используйте `npm.cmd` и прямой путь `.\.venv\Scripts\python.exe`, как в Windows-инструкции. Ослаблять системную политику выполнения для этого не требуется.

</details>

<details>
<summary><strong>После обновления требуется войти заново</strong></summary>

Это ожидаемо при переходе со старого формата сессий, выходе, изменении роли/пароля, отключении сотрудника или ротации `API_KEY`. Для восстановления административного входа используйте ключ из своего `.env`.

</details>

## Безопасность и границы применения

- Не публикуйте Vite dev-сервер и API напрямую в интернет. По умолчанию порты привязаны к loopback.
- Для сетевого доступа настройте HTTPS reverse proxy, `COOKIE_SECURE=true`, конкретные `CORS_ORIGINS`, firewall и изолированную сеть камер. PostgreSQL/Redis не должны быть доступны извне.
- Не запускайте несколько uvicorn workers или backend-реплик: управление камерами и блокировки рассчитаны на один экземпляр API.
- Собака — обнаруженный объект, а не установленный факт безнадзорности. Содержимое сумок и намерения людей не распознаются.
- Правило сумки использует рамки и расстояния, а не идентификацию владельца. Перспектива и перекрытия влияют на результат.
- Возможны ложные срабатывания и пропуски, включая краткий показ оружия. Нужны независимые измерения precision/recall, ложных тревог на камеро-час и задержки до оператора.
- Запись поддерживает настраиваемые pre/post-roll; доступная длительность зависит от поступления кадров и лимита памяти. Уведомление задерживается до завершения клипа и кодирования.
- Центр тревог опрашивает последние 100 событий раз в 5 секунд. Это не гарантированная очередь: cursor/backfill ещё не реализован.
- Журнал действий доступен администраторам; это прикладной журнал в БД, а не защищённый от администратора неизменяемый аудит. TOTP-2FA реализована; recovery-коды, самостоятельное восстановление пароля и автоматическое восстановление прерванного обучения пока не реализованы.
- Подтверждены пробелы проверки права просмотра, отзыва открытых потоков и согласованности управления камерами. Они **пока не исправлены**: [отчёт аудита](docs/SECURITY_AUDIT.md).
- До пилота проверьте длительную нагрузку, потери камер/сети, заполнение диска, резервное копирование и требования к персональным данным.

Подробности выполненных проверок и непроверенных условий: **[docs/REPAIR_NOTES.md](docs/REPAIR_NOTES.md)**.
